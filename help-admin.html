Module 1

Overview dashboard

The Overview screen is the first thing you see after sign-in. Six stat cards summarize every order in the system — total, pending, approved, rejected, shipped and delivered. This gives you an at-a-glance snapshot of business volume without drilling into any module.

Reading the cards

  • Total Orders — every order ever placed (all statuses combined).
  • Pending — orders sitting in Pending Payment or Payment Uploaded. These need your attention.
  • Approved — orders whose payment is verified and are waiting to be shipped.
  • Rejected — orders where payment proof was rejected (buyer can re-upload).
  • Shipped — orders currently in transit.
  • Delivered — completed orders.
User story · Morning checkadmin

"I open the dashboard first thing every morning."

Admin Ana signs in and immediately sees 12 orders need attention — 5 are Pending Payment (buyers haven't uploaded proof yet) and 7 are Payment Uploaded (awaiting her review). She navigates to Pending Reviews to start working through them.

The Overview never expires or caches; every page load hits the database directly, so the numbers are always current.

Module 2

Accounts

Manage every buyer who signs up, plus any other admin accounts. This is where you approve new sign-ups, block accounts, reset passwords, and create accounts on behalf of a buyer.

  1. Open "Accounts" from the sidebar.You land on a searchable, sortable table of every account — ID, Name, Email, Business, Location, Business Type, Role, Status, Joined date and an Actions column.
  2. Filter by status.The dropdown at the top lets you narrow to Pending approval, Active or Blocked. New sign-ups appear under "Pending approval".
  3. Approve a buyer.Click the action icon in the Actions column for a pending account → approve. The buyer can now sign in immediately.
  4. Block or unblock.An active account can be blocked (sign-in stops working). Blocked accounts can be unblocked to restore access.
  5. Create a new account.Tap + New Account to open a form: full name, email, business name, type, phone, delivery address and a map pin. New accounts default to Active status.

Module 3

Products

Manage the full product catalog — add new SKUs, update prices and stock levels, soft-delete discontinued items, and adjust inventory counts. Buyers see this same catalog in real time.

  1. Open "Products" from the sidebar.A searchable table shows SKU, Name, Category, Strength, Price, Stock and an Actions column. Filter by category with the dropdown, or search by name/SKU.
  2. Add a new product.Tap + New Product. Fill in: SKU (e.g. PAR-500-BX), Unit (Box / Bottle / Strip), Name, Category, Dosage strength, Price, Starting stock quantity, and Description. The SKU must be unique.
  3. Adjust stock.In the Actions column, open the Stock modal. Enter a +50 or −10 adjustment (positive to add, negative to deduct). The current stock count is always shown above the field.
  4. Edit or soft-delete.Edit any field via the Edit modal. Soft-delete removes the product from the buyer catalog without destroying the record — it can be restored.

Module 5

Pending Reviews — payment verification

This is the most operationally important screen. Every order whose buyer has uploaded a bank transfer proof lands here, waiting for an admin to verify and approve — or reject with a reason.

  1. Open "Pending Reviews".A queue of Payment Uploaded orders, sorted newest-first. Each card shows the order number, buyer, status badge, items, total, the uploaded proof reference and upload time.
  2. Click "View proof".A modal opens showing the proof image or PDF, the full item list, subtotal/delivery/grand total, and a map with the delivery route. There's also a Download Proof button for saving a local copy.
  3. Approve or Reject.If the proof matches the bank record and the amount is correct, tap Approve. The order moves to Approved and enters the Fulfillment queue. If there's a problem, tap Reject and type a clear reason — the buyer sees it in their Order History and can re-upload.

Module 6

Fulfillment — ship & deliver

After payment is approved, orders enter Fulfillment. This module has three tabs: Approved (ready to ship), Shipped (in transit) and Delivered (complete). Each tab shows a card with the order, buyer, total and an action button.

  1. Open "Fulfillment" from the sidebar.You land on the Approved tab — orders waiting to be shipped. Each card shows the order number, buyer name, item count, total, status badge and a Ship Order button.
  2. Ship an order.Tap Ship Order. The order moves to the Shipped tab. The buyer sees "Shipped" in their Order History.
  3. Mark as delivered.Switch to the Shipped tab. Tap Mark Delivered on the order. It moves to the Delivered tab and the order is complete.
  4. Open full details.Click View details ↗ on any card to see the full order details modal: payment proof, items + pricing, delivery route on a map, and the full status timeline with timestamps and who changed each status.

Module 7

Delivery Setup

Configure the warehouse origin on a Leaflet map and set the delivery pricing rules: rate per meter traveled, minimum order for free delivery, and maximum distance for the free-delivery offer. A live preview shows sample charges for common scenarios.

  1. Pin your warehouse origin.Click anywhere on the map to drop a green pin. This is the starting point for every delivery route calculation. You can drag the pin to adjust.
  2. Set delivery rate per meter.Enter the peso rate per meter (e.g. 0.05 = ₱0.05/meter = ₱50/km). This is multiplied by the OSRM road distance to compute the delivery charge.
  3. Configure free delivery.Set Minimum order amount (e.g. ₱1,500) and Maximum distance (e.g. 3,000 meters). Orders above the minimum AND within the distance are delivered free.
  4. Check the live preview.Three example scenarios update in real time: ₱500 order at 2 km, ₱1,500 order at 2 km, and ₱1,500 order at 5 km. Use these to validate your pricing before saving.
  5. Save.Tap Save delivery settings. All future orders use the new rates immediately.

How it all fits together

Complete order lifecycle — admin side

Buyer registers → Admin approves account → Buyer places order → Buyer uploads proof → Admin reviews & approves → Admin ships → Admin marks delivered

Status transitions controlled by the admin

  • APPROVED → only reachable from Payment Uploaded by an admin clicking Approve.
  • PAYMENT_REJECTED → only from Payment Uploaded by an admin clicking Reject with a reason.
  • SHIPPED → only from Approved by an admin clicking Ship Order in Fulfillment.
  • DELIVERED → only from Shipped by an admin clicking Mark Delivered.

What the buyer controls (no admin needed)

  • CANCELLED → buyer can cancel only while status is Pending Payment or Payment Rejected. Stock is released back.
  • Upload proof → buyer can upload a new proof at any time while status is Pending Payment or Payment Rejected (up to 20 proofs/day).

Audit trail

  • Every status change is recorded with: old_status, new_status, changed_by (user ID), changed_by_role (admin/buyer), changed_by_email and changed_at (timestamp).
  • The timeline is visible in the Fulfillment order details modal and the buyer's Order History modal.

Technical overview

Architecture & design

PharmaB2B is a single-page application with a Python/FastAPI backend, MySQL database, Redis cache layer, and a vanilla-JS frontend. Everything runs on a single server (MAMP stack on macOS in development, any Linux host in production).

Request flow (simplified)

  1. Browser sends fetch() request with JWT cookie → FastAPI receives.
  2. Middleware: checks rate limit, validates session (Redis or principal cache), attaches user to request state.
  3. Route handler: validates input (Pydantic), queries MySQL via async SQLAlchemy.
  4. Response: JSON body + Set-Cookie refreshes the JWT expiry if needed.

Performance

Designed to handle 10,000+ concurrent sessions on commodity hardware. The key performance levers are connection pooling, principal caching, and proper database indexing.

Technical overview

Security

PharmaB2B follows OWASP Top 10 best practices. Every input is validated server-side, passwords are hashed with Argon2id, sessions use HttpOnly JWT cookies with SameSite=Strict, and every file upload is type-checked before being saved.

Key security notes for clients

  • No payment card data is ever stored — settlement is offline bank transfer only.
  • Admin passwords are never visible to anyone, including other admins — only reset is available.
  • File uploads are validated server-side — even if a malicious file is renamed to .jpg, the server checks the actual MIME type.
  • Redis is lazy-loaded — if Redis is unreachable, the app degrades gracefully (session validation falls back to database principal lookup).

Quick reference

Key facts & FAQ

Key facts

  • There is no online payment gateway — all settlement is offline bank transfer + proof upload.
  • Buyer self-registration always requires admin approval before first sign-in.
  • Delivery fee = (road distance in meters) × (rate per meter). Free delivery when order ≥ minimum amount AND distance ≤ max distance.
  • Stock is reserved the moment a buyer places an order — other buyers see reduced stock in real time.
  • Payment proof limit: 20 uploads per buyer per day (prevents abuse).
  • Order number format: ORD-YYYYMMDD-12-hex-chars — includes date for easy sorting.
  • Session timeout: 60 minutes of inactivity → forced sign-out.

Frequently asked questions

  • Can I restore a soft-deleted product? — Yes. Soft-delete hides it from buyers but the record stays in the database. Contact the developer to restore.
  • What if the map tile server is blocked? — The app detects blocked OpenStreetMap tiles and transparently switches to MapTiler (if a fallback key is configured). Pins and routes always work regardless.
  • Can two admins approve the same order? — No. The first approval wins; the second admin sees the order has already moved to Approved.
  • What happens if Redis is down? — The app degrades gracefully: rate limiting is skipped and principal lookup falls back to the database. No user-visible errors.
  • How do I change the password policy? — Edit the minimum length and complexity rules in the Pydantic validator on the registration and password-change endpoints.
  • Can buyers see each other's orders? — No. Every query is scoped to the authenticated user's ID (buyers) or unrestricted (admins only).
